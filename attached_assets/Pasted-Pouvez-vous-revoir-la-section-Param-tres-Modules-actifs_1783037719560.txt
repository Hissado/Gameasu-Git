Pouvez-vous revoir la section **Paramètres > Modules actifs** afin qu’elle soit cohérente avec la logique de **Rôles & Permissions** dans Gameasu ?

### Objectif

Je veux que la gestion des **modules actifs** dans les paramètres soit parfaitement alignée avec le système de **rôles et permissions**.

Actuellement, la section **Modules actifs** permet d’activer ou désactiver certains modules, mais elle doit être plus cohérente avec la structure réelle de l’ERP et avec les accès utilisateurs.

L’objectif est d’éviter les incohérences entre :

* les modules activés dans les paramètres ;
* les modules visibles dans le menu ;
* les permissions attribuées aux rôles ;
* les sous-sections accessibles ;
* les rapports disponibles ;
* les données affichées dans le dashboard.

---

## 3. Synchronisation avec Rôles & Permissions

Les modules activés dans **Paramètres > Modules actifs** doivent impacter automatiquement les permissions disponibles dans **Rôles & Permissions**.

### Règle attendue

Si un module est désactivé au niveau de l’organisation :

* il ne doit plus apparaître dans le menu ;
* il ne doit plus apparaître dans les permissions ;
* ses sous-sections ne doivent plus être accessibles ;
* ses rapports ne doivent plus être disponibles ;
* ses KPI ne doivent plus apparaître dans le dashboard ;
* ses notifications doivent être désactivées ;
* ses raccourcis doivent être masqués.

### Exemple

Si le module **Finance** est désactivé :

* aucun rôle ne doit pouvoir recevoir des permissions Finance ;
* le menu Finance doit disparaître ;
* les rapports financiers doivent être masqués ;
* les KPI financiers doivent être masqués ;
* les exports financiers doivent être désactivés.

Si le module **Équipe / RH** est désactivé :

* les collaborateurs, congés, présences, kiosk et paie doivent être masqués ;
* les permissions RH ne doivent plus être proposées ;
* les rapports RH ne doivent plus être accessibles.

---

## 4. Cohérence entre activation module et permissions utilisateur

Il faut bien distinguer deux niveaux :

### Niveau 1 — Modules actifs pour l’organisation

L’admin décide quels modules sont disponibles pour l’organisation.

### Niveau 2 — Permissions par rôle

Une fois un module actif, l’admin décide quels rôles peuvent y accéder.

### Exemple

Le module **Achats** peut être actif pour l’organisation, mais seulement certains rôles peuvent y accéder :

* Administrateur : accès complet
* Responsable Achats : accès complet Achats
* Comptable : consultation et paiements
* Collaborateur : aucun accès

Cette logique doit être claire dans l’interface.

## 5. Améliorer l’interface “Modules actifs”

L’interface actuelle doit être rendue plus professionnelle, plus claire et plus premium.

### Recommandations UX

Afficher les modules sous forme de cartes ou sections propres avec :

* nom du module ;
* courte description ;
* statut : actif / inactif ;
* nombre de sous-modules ;
* impact sur les permissions ;
* bouton pour développer les sous-modules ;
* indication des rôles ayant accès au module ;
* lien rapide vers **Configurer les permissions**.

### Exemple de carte

**Finance**
Gérez la trésorerie, la comptabilité, les budgets, les rapports financiers et les analyses.

Statut : Actif
Sous-modules : Comptabilité, Trésorerie, Budgets, Rapports
Rôles autorisés : Administrateur, Direction, Finance
Bouton : Configurer les permissions

---

## 6. Ajouter des alertes avant désactivation

Avant de désactiver un module, afficher une confirmation claire.

### Exemple

**Attention : vous êtes sur le point de désactiver le module Finance.**

Cela va masquer :

* le menu Finance ;
* les sous-sections Finance ;
* les rapports financiers ;
* les permissions Finance ;
* les KPI financiers du dashboard ;
* les notifications liées à Finance.

Boutons :

* Annuler
* Confirmer la désactivation

La désactivation ne doit pas supprimer les données. Elle doit seulement masquer ou désactiver l’accès au module.

---

## 7. Protéger les modules essentiels

Certains modules doivent être considérés comme essentiels et ne doivent pas être désactivés facilement.

### Modules essentiels

* Tableau de bord
* Paramètres
* Utilisateurs & accès
* Rôles & permissions
* Abonnement & facturation

Pour ces modules, afficher une mention :

**Module système — désactivation non autorisée**

ou permettre uniquement une configuration limitée.

---

## 8. Synchronisation avec le menu latéral

Le menu latéral doit refléter exactement les modules actifs.

### Règles

* module désactivé → menu masqué ;
* sous-module désactivé → sous-menu masqué ;
* module actif mais rôle non autorisé → menu masqué pour cet utilisateur ;
* module actif et rôle autorisé → menu visible.

Aucun utilisateur ne doit voir un module auquel il n’a pas accès.

---

## 9. Synchronisation avec les rapports

Les rapports doivent aussi respecter les modules actifs.

### Exemple

Si **Achats** est désactivé :

* les rapports achats ne doivent pas apparaître ;
* les filtres liés aux achats doivent être masqués ;
* les exports achats doivent être indisponibles.

Si **RH** est désactivé :

* les rapports collaborateurs, congés, présences, kiosk et paie doivent être masqués.

---

## 10. Synchronisation avec le dashboard

Le tableau de bord doit afficher uniquement les KPI liés aux modules actifs et autorisés.

### Exemple

Si Finance est désactivé, ne pas afficher :

* trésorerie ;
* revenus ;
* dépenses ;
* budgets ;
* créances ;
* dettes.

Si RH est désactivé, ne pas afficher :

* collaborateurs actifs ;
* congés ;
* présences ;
* paie ;
* pointage.

---

## 11. Sécurité backend

Les modules désactivés ne doivent pas seulement être masqués côté frontend.

Merci de vérifier aussi côté backend :

* API protégées ;
* routes protégées ;
* rapports protégés ;
* exports protégés ;
* données protégées ;
* actions protégées.

Un utilisateur ne doit pas pouvoir accéder à un module désactivé via URL directe ou appel API.

---

## 12. Résultat attendu

Je veux une section **Modules actifs** plus cohérente, plus réaliste et mieux synchronisée avec **Rôles & Permissions**.

Le système doit permettre de :

* activer ou désactiver les modules au niveau organisation ;
* afficher les sous-modules liés ;
* synchroniser automatiquement les permissions ;
* masquer les menus non actifs ;
* masquer les rapports non concernés ;
* adapter le dashboard ;
* protéger l’accès côté backend ;
* éviter les incohérences entre paramètres, menu, rôles et rapports.

### Objectif final

Avoir une gestion des modules et permissions digne d’un ERP premium : claire, hiérarchique, sécurisée, cohérente et facile à administrer pour chaque organisation cliente.
