# Refonte du Journal d’audit Gameasu — Traçabilité complète des activités utilisateurs

Pouvez-vous enrichir et restructurer le **Journal d’audit** de Gameasu afin qu’il permette de retracer précisément les activités réalisées par chaque utilisateur dans l’ERP, le Cockpit et le Portail Expert ?

## Objectif

Le journal actuel affiche principalement les connexions et les validations 2FA. Je souhaite disposer d’un véritable système de traçabilité permettant de comprendre :

* qui a effectué une action ;
* dans quelle organisation ;
* dans quel module et quelle page ;
* quelle opération a été réalisée ;
* sur quelle donnée ou quel document ;
* quelles informations ont été modifiées ;
* à quel moment ;
* depuis quelle session ou quel appareil ;
* si l’action a réussi, échoué ou été refusée.

Le journal doit permettre de reconstituer clairement le parcours d’un utilisateur, tout en évitant d’enregistrer les mots de passe, secrets, tokens ou autres données sensibles.

---

## 1. Enregistrer les accès aux modules

Permettre de consulter les modules et sous-sections visités par l’utilisateur.

Exemples :

* entrée dans le module Ventes ;
* ouverture de la liste des clients ;
* consultation d’une fiche client ;
* ouverture du module Comptabilité ;
* consultation du plan comptable ;
* accès au module Paie ;
* ouverture d’un rapport ;
* accès aux paramètres ;
* entrée dans le Cockpit ;
* changement d’organisation.

Pour chaque accès, enregistrer au minimum :

* utilisateur ;
* organisation active ;
* module ;
* sous-module ;
* page ou route ;
* date et heure ;
* session concernée ;
* type d’appareil ;
* navigateur ;
* adresse IP selon les règles de confidentialité ;
* durée de consultation si elle est utile.

Les simples visites de pages peuvent être enregistrées dans une catégorie distincte appelée :

**Activité de navigation**

afin de ne pas mélanger la navigation avec les actions sensibles.

---

* modification ;

* restauration ;

* impression ;

* rejet ;

## 3. Afficher les anciennes et nouvelles valeurs

Pour les actions de modification, le journal doit indiquer ce qui a changé.

### Exemple

**Action : Modification d’un collaborateur**

* Champ modifié : Salaire de base
* Ancienne valeur : 250 000 FCFA
* Nouvelle valeur : 300 000 FCFA
* Motif : Promotion
* Modifié par : Responsable RH
* Date : 16 juillet 2026 à 14:32

Prévoir une comparaison lisible entre :

* valeur précédente ;
* nouvelle valeur ;
* champs ajoutés ;
* champs supprimés ;
* statut précédent ;
* nouveau statut.

Pour les informations sensibles, masquer partiellement les valeurs selon les permissions de l’utilisateur qui consulte le journal.

---

## 4. Ajouter une fiche détaillée pour chaque événement

Lorsqu’on clique sur **Détails**, ouvrir un panneau latéral ou une fenêtre contenant :

### Identification

* identifiant unique de l’événement ;
* date et heure précises ;
* utilisateur ;
* email ;
* rôle actif ;
* organisation ;
* session ;
* origine de l’action.

### Contexte fonctionnel

* module ;
* sous-module ;
* page ;
* type d’entité ;
* identifiant ou référence de l’élément concerné ;
* nom du client, collaborateur, facture ou document concerné.

### Action

* action effectuée ;
* résultat : succès, échec ou refus ;
* ancienne et nouvelle valeur ;
* motif ou commentaire ;
* approbateur éventuel ;
* workflow concerné.

### Contexte technique

* appareil ;
* navigateur ;
* système d’exploitation ;
* adresse IP ;
* identifiant de requête ou de corrélation ;
* message d’erreur si applicable.

Les identifiants techniques ne doivent pas encombrer la liste principale. Ils doivent apparaître uniquement dans la vue détaillée.

---

## 5. Créer une chronologie par utilisateur

Ajouter une vue :

**Activité utilisateur**

Cette vue doit permettre de sélectionner un utilisateur et de consulter chronologiquement son parcours.

### Exemple

* 08:02 — Connexion réussie
* 08:04 — Organisation Hissado Consulting sélectionnée
* 08:06 — Module Ventes ouvert
* 08:08 — Client ABC consulté
* 08:12 — Devis DEV-2026-0048 créé
* 08:16 — Devis envoyé par email
* 08:25 — Module Achats ouvert
* 08:29 — Facture fournisseur importée
* 08:31 — Anomalie détectée et justification ajoutée
* 09:02 — Déconnexion

Cette chronologie doit permettre de comprendre rapidement l’enchaînement des actions sans devoir ouvrir chaque événement séparément.

---

## 6. Créer une chronologie par élément

Depuis une fiche client, facture, collaborateur, fournisseur, projet ou document, ajouter un onglet :

**Journal d’activité**

Il doit afficher tout ce qui a été réalisé sur cet élément.

### Exemple pour une facture

* facture créée ;
* lignes modifiées ;
* TVA corrigée ;
* pièce jointe ajoutée ;
* facture validée ;
* facture envoyée ;
* paiement enregistré ;
* facture annulée.

Cela doit compléter le journal d’audit global.

## 8. Classer les événements par niveau de sensibilité

Ajouter une classification :

* **Information** : consultation ou navigation ;
* **Faible** : modification non sensible ;
* **Moyen** : création, validation ou export ;
* **Élevé** : paie, finance, fiscalité, permissions ou suppression ;
* **Critique** : changement de Super Administrateur, modification massive, désactivation 2FA, restauration de sauvegarde ou accès non autorisé.

Utiliser des badges et des icônes cohérents afin d’identifier rapidement les événements importants.

---

## 9. Ajouter des alertes de sécurité

Le système doit pouvoir détecter certains comportements inhabituels :

* connexions répétées depuis plusieurs pays ou adresses IP ;
* plusieurs échecs de connexion ;
* tentative d’accès à un module interdit ;
* modification massive de données ;
* suppression de nombreux éléments ;
* export volumineux ;
* modification des rôles ou permissions ;
* désactivation de la double authentification ;
* changement de coordonnées bancaires ;
* changement inhabituel de données salariales ;
* consultation répétée de données sensibles.

Selon la gravité, générer :

* une alerte dans le Cockpit ;
* une notification aux administrateurs autorisés ;
* éventuellement un email de sécurité.

---

## 10. Distinguer journal d’audit et analytics d’usage

Ne pas enregistrer chaque mouvement de souris ou chaque clic sans valeur métier dans le journal principal.

Créer deux niveaux distincts :

### Journal d’audit

Pour les actions sensibles, administratives, financières, RH et métier.

### Activité d’utilisation

Pour les pages visitées, modules consultés, durée d’utilisation et parcours de navigation.

Cette séparation permettra d’éviter un journal trop volumineux et difficile à exploiter.

---

## 11. Sécurité et intégrité du journal

Le journal d’audit doit être protégé.

### Règles obligatoires

* les événements ne doivent pas pouvoir être modifiés par les utilisateurs ;
* aucune suppression manuelle ne doit être possible depuis l’interface standard ;
* toute exportation du journal doit elle-même être journalisée ;
* la consultation d’événements sensibles doit être enregistrée ;
* les données doivent être isolées par tenant ;
* le Cockpit ne doit voir que les informations autorisées ;
* les événements doivent être horodatés côté serveur ;
* utiliser une conservation fiable et résistante aux modifications ;
* prévoir une politique de rétention configurable.

Ne jamais enregistrer en clair :

* mots de passe ;
* codes 2FA ;
* tokens ;
* clés API ;
* numéros complets de cartes bancaires ;
* secrets techniques ;
* pièces d’identité complètes dans les détails de modification.

---

## 12. Permissions spécifiques

Créer des permissions dédiées :

* consulter le journal d’audit ;
* consulter les événements de navigation ;
* voir les informations techniques ;
* voir les adresses IP ;
* voir les anciennes et nouvelles valeurs ;
* consulter les activités RH sensibles ;
* consulter les activités financières ;
* exporter le journal ;
* gérer les règles de conservation ;
* configurer les alertes de sécurité.

Un responsable RH ne doit pas nécessairement voir les événements techniques du Cockpit, et un administrateur fonctionnel ne doit pas voir les montants de paie sans autorisation.

---

## 13. Gestion multi-organisation

Un même utilisateur peut appartenir à plusieurs organisations.

Le journal doit donc toujours indiquer :

* l’organisation dans laquelle l’action a été réalisée ;
* le rôle actif au moment de l’action ;
* le module disponible dans cette organisation ;
* l’identifiant de la session active.

Lors d’un changement d’organisation, créer un événement :

**Organisation active modifiée : Organisation A → Organisation B**

Aucune activité d’un tenant ne doit apparaître dans le journal d’un autre tenant.

---

Permettre l’export sécurisé en :

Créer des rapports tels que :

* activité par utilisateur ;

* connexions et échecs ;

* changements de permissions ;
* suppressions et restaurations ;

* les filtres appliqués ;
* la période ;
* la date d’export ;
* l’utilisateur ayant généré le document.

## Résultat attendu

Je veux transformer le journal actuel en un véritable centre de traçabilité et de sécurité permettant de :

* comprendre l’ensemble du parcours d’un utilisateur ;
* voir les modules et pages consultés ;
* connaître toutes les actions métier importantes ;
* comparer les valeurs avant et après modification ;
* retrouver l’historique complet d’une donnée ;
* détecter les comportements inhabituels ;
* répondre aux besoins d’audit interne et de contrôle ;
* assurer une séparation stricte entre les organisations.

### Objectif final

Faire du Journal d’audit Gameasu un outil premium, détaillé, lisible et sécurisé, capable de reconstituer précisément les activités importantes réalisées dans l’ERP, le Cockpit et le Portail Expert, sans compromettre la confidentialité des données ni surcharger l’application avec des événements inutiles.
