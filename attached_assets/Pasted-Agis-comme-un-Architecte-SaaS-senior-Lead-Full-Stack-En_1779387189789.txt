OBJECTIF
Transformer l’application en une véritable plateforme SaaS multi-entreprises où :

- chaque entreprise cliente dispose de son propre environnement
- chaque entreprise a son propre administrateur
- chaque entreprise peut gérer ses propres utilisateurs, staff, clients, données, paramètres et opérations
- les fonctionnalités accessibles dépendent du package / abonnement choisi
- les données sont strictement séparées entre entreprises
- la plateforme dispose aussi d’un espace Super Admin global pour notre propre gestion

ARCHITECTURE GLOBALE REQUISE
L’application doit fonctionner comme une vraie SaaS multi-tenant avec :

1. gestion des tenants / entreprises
2. authentification et accès sécurisé
3. abonnement et billing par entreprise
4. activation des fonctionnalités selon le package
5. rôles et permissions par entreprise
6. portail administrateur pour chaque entreprise
7. Super Admin global pour nous
8. séparation stricte des données
9. structure extensible pour ajout futur de modules et packages

MULTI-TENANCY — EXIGENCE PRINCIPALE
Implémente une logique multi-tenant robuste.

Chaque entreprise doit avoir :
- un tenant_id unique
- ses propres données
- ses propres utilisateurs
- ses propres clients
- ses propres paramètres
- ses propres abonnements
- ses propres modules activés
- ses propres opérations

Aucune donnée d’une entreprise ne doit être visible ou accessible par une autre.

Toute la logique de l’application doit être filtrée par tenant_id.

Applique cette séparation dans :
- la base de données
- les requêtes
- les API
- les pages
- les dashboards
- les permissions
- les exports
- les rapports
- les notifications
- les fichiers/documents si applicable

AUTHENTIFICATION

Prévoir :
- inscription entreprise
- création du compte administrateur principal lors de l’onboarding
- login sécurisé
- reset password
- email verification si possible
- invitation d’utilisateurs
- gestion de session
- déconnexion
- protection des routes
- contrôle strict des accès selon tenant + rôle + abonnement

Le flux doit être professionnel :

1. une entreprise s’inscrit
2. elle crée son compte principal
3. elle choisit son package
4. son abonnement est créé
5. son tenant est provisionné
6. elle accède à son espace dédié
7. elle peut ensuite inviter son staff

ABONNEMENTS / PACKAGES / BILLING
Implémente une vraie logique SaaS de souscription.

Créer des packages avec :
- nom du plan
- description
- prix mensuel
- prix annuel
- devise
- modules inclus
- limites d’utilisation
- nombre max d’utilisateurs
- nombre max de clients
- fonctionnalités premium
- statut actif/inactif

Créer un système de billing capable de gérer :
- souscription initiale
- renouvellement
- upgrade
- downgrade
- suspension
- expiration
- annulation
- historique de facturation
- factures
- paiements
- statut de paiement

Les fonctionnalités de l’application doivent être activées ou bloquées automatiquement selon le plan souscrit.

Exemples :
- certains modules visibles seulement sur certains packages
- limite de nombre de staff selon l’abonnement
- limite de clients selon le package
- fonctionnalités avancées réservées aux plans supérieurs

Prévoir une architecture prête à connecter un provider de paiement si nécessaire.

GESTION DES FONCTIONNALITÉS PAR PACKAGE
Crée un vrai mécanisme feature gating.

Chaque plan doit contrôler :
- modules visibles
- pages accessibles
- volume d’utilisation
- actions possibles
- options premium
- capacités avancées

Ne pas faire cela en dur dans l’interface uniquement.
La logique doit exister côté backend + frontend.

Prévois :
- vérification serveur
- middleware/guards
- vérification UI
- messages clairs quand une fonctionnalité nécessite un upgrade
