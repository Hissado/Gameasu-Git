Avez-vous bien pris en compte la possibilité qu’un même utilisateur, avec une seule adresse email, puisse avoir accès à plusieurs comptes / organisations dans Gameasu, comme cela se fait dans QuickBooks ?

Objectif

Je veux que Gameasu permette à un utilisateur d’utiliser un seul compte personnel avec la même adresse email, tout en pouvant accéder à plusieurs organisations différentes selon les invitations et permissions reçues.

Exemple :

Un consultant, comptable, dirigeant ou employé peut utiliser la même adresse email pour accéder à :

* Organisation A ;
* Organisation B ;
* Organisation C ;
* Hissado Consulting ;
* une autre entreprise cliente.

L’utilisateur ne doit pas être obligé de créer plusieurs comptes avec plusieurs emails différents.

⸻

1. Logique multi-organisation par utilisateur

Mettre en place une architecture où :

* un utilisateur peut exister une seule fois dans le système ;
* son email est unique au niveau global ;
* il peut être membre de plusieurs organisations ;
* chaque organisation a ses propres rôles, permissions, données et paramètres ;
* l’utilisateur peut basculer d’une organisation à l’autre après connexion.

Exemple

Utilisateur : consultant@email.com

Accès :

* Hissado Consulting — rôle : Administrateur
* ABC SARL — rôle : Consultant Finance
* XYZ Group — rôle : Lecture seule
* Cabinet Alpha — rôle : Responsable Comptabilité

Le même utilisateur doit pouvoir accéder à ces organisations avec le même login, mais avec des permissions différentes selon chaque organisation.

⸻

2. Sélecteur d’organisation après connexion

Après connexion, si l’utilisateur a accès à plusieurs organisations, afficher un écran ou menu :

Choisir une organisation

L’utilisateur doit voir :

* nom de l’organisation ;
* logo ;
* rôle dans cette organisation ;
* statut de l’accès ;
* dernière connexion ;
* bouton Accéder.

Si l’utilisateur n’a accès qu’à une seule organisation, il peut être redirigé directement vers cette organisation.

⸻

3. Switcher d’organisation dans l’application

Ajouter un sélecteur d’organisation dans le header ou le menu utilisateur.

L’utilisateur doit pouvoir :

* voir l’organisation active ;
* changer d’organisation rapidement ;
* revenir à une autre organisation sans se déconnecter ;
* voir clairement dans quelle organisation il travaille.

Important

À chaque changement d’organisation :

* les données affichées doivent changer ;
* les permissions doivent être recalculées ;
* le menu doit s’adapter ;
* les rapports doivent correspondre uniquement à l’organisation active ;
* les paramètres doivent être ceux de l’organisation active ;
* aucune donnée ne doit être mélangée entre organisations.

⸻

4. Permissions par organisation

Les permissions doivent être rattachées à l’organisation, pas seulement à l’utilisateur.

Un même utilisateur peut avoir des rôles différents selon l’organisation.

Exemple

Dans Organisation A :

* accès complet Finance.

Dans Organisation B :

* accès uniquement aux rapports.

Dans Organisation C :

* aucun accès RH.

Le système doit toujours vérifier :

* user_id ;
* organization_id ;
* rôle dans cette organisation ;
* permissions spécifiques à cette organisation ;
* statut de l’invitation ou de l’accès.

⸻

5. Invitations utilisateurs

Lorsqu’un admin invite un utilisateur par email :

* si l’email existe déjà, ne pas créer un doublon ;
* ajouter simplement cet utilisateur comme membre de la nouvelle organisation ;
* envoyer une notification indiquant qu’il a été ajouté à une nouvelle organisation ;
* lui permettre de choisir cette organisation à la prochaine connexion.

Exemple

Si issa@email.com existe déjà dans Gameasu et qu’une nouvelle organisation l’invite, le système doit :

* reconnaître le compte existant ;
* créer une relation membre entre l’utilisateur et la nouvelle organisation ;
* appliquer le rôle choisi ;
* notifier l’utilisateur ;
* afficher la nouvelle organisation dans son sélecteur.

⸻

6. Isolation stricte des données

Même si un utilisateur a accès à plusieurs organisations, les données doivent rester totalement séparées.

Vérifier que chaque requête, chaque rapport et chaque action utilise toujours :

* organization_id ;
* tenant_id si applicable ;
* rôle actif ;
* permissions actives ;
* organisation active.

Aucune donnée d’une organisation ne doit apparaître dans une autre organisation.

⸻

7. Cas d’usage à tester

Merci de tester les scénarios suivants :

Scénario 1 — Un utilisateur avec une seule organisation

* connexion ;
* redirection directe vers son organisation ;
* accès selon ses permissions.

Scénario 2 — Un utilisateur avec plusieurs organisations

* connexion ;
* affichage du choix d’organisation ;
* sélection d’une organisation ;
* changement d’organisation depuis le header.

Scénario 3 — Même email invité dans une nouvelle organisation

* le compte existe déjà ;
* l’invitation ajoute l’utilisateur à la nouvelle organisation ;
* aucune duplication du compte ;
* nouvel accès visible après connexion.

Scénario 4 — Permissions différentes selon organisation

* même email ;
* rôle Admin dans une organisation ;
* rôle Lecture seule dans une autre ;
* menus, rapports et actions adaptés à chaque rôle.

Scénario 5 — Désactivation d’un accès

* retirer l’utilisateur d’une organisation ;
* il garde son compte global ;
* il perd seulement l’accès à l’organisation concernée ;
* ses autres accès restent actifs.

⸻

8. Interface utilisateur

Ajouter une expérience claire et professionnelle.

À prévoir

* écran de sélection d’organisation ;
* switcher d’organisation dans le header ;
* indication visible de l’organisation active ;
* message si aucun accès actif ;
* gestion des invitations en attente ;
* logo et nom de l’organisation ;
* rôle affiché ;
* statut de l’accès.

⸻

9. Cockpit Plateforme

Dans le Cockpit, permettre à l’équipe Gameasu de voir :

* les utilisateurs globaux ;
* les organisations auxquelles chaque utilisateur a accès ;
* le rôle de l’utilisateur par organisation ;
* la date d’invitation ;
* le statut de l’accès ;
* la possibilité de suspendre l’accès à une organisation sans supprimer le compte global.

⸻

10. Résultat attendu

Je veux que Gameasu supporte une vraie logique multi-organisation comparable à QuickBooks :

* un seul email ;
* un seul compte utilisateur ;
* plusieurs organisations possibles ;
* rôles différents par organisation ;
* sélection ou changement d’organisation ;
* données strictement isolées ;
* permissions recalculées selon l’organisation active ;
* invitations sans doublons ;
* Cockpit capable de gérer ces accès.

Objectif final

Permettre à Gameasu d’être utilisé par des dirigeants multi-entreprises, des consultants, des comptables, des cabinets, des groupes, des partenaires ou des équipes qui interviennent sur plusieurs organisations, sans créer plusieurs comptes pour le même utilisateur.
